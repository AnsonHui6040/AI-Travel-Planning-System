## 設計

| 項目 | 說明 |
|---|---|
| 寫入路徑 | `applyChange`（core）解析提案 schema、依第 2.6 節選擇批准或自動套用、依第 2.7 節檢查版本類型，再經 `ChangeWriter` port 呼叫資料庫函式 |
| 資料庫函式 | `approve_proposal`、`reject_proposal`（authenticated，需 Owner 或 Companion）；`auto_apply_proposal`（只限 service role，只接受第 2.6 節自動類別）；三者以 `atps_change_writer`（不可登入）身分執行，批准者取自 session |
| 交易 | 先鎖行程列再鎖提案列；比對 base version、寫入項目、目前版本加一、寫入 Change Log、提案改為已套用、同分支其餘待批准提案失效、通知成員，全部在同一交易 |
| 版本號 | 第一版 v1.0；Major 主版號加一、次版號歸零；Minor 次版號加一。`trips.current_version` 為每次套用加一的計數，作為 base version |
| Major 判定 | 結構變更（飯店、航班日期、取消整日）、項目移到另一天、同時影響兩天以上；其餘為 Minor |
| 批准一日行程 | 以 Minor 建立新 Master Version |
| 變更操作 | 第一版支援 `schedule_item`（日期與時間）與 `set_at_risk`；其他操作於需要的 Task 加入，資料庫拒絕未知操作 |
| Change Log | `versions` 記錄修改內容、原因、提案、批准者（自動套用為空）、影響範圍、舊安排、新安排、base version |
| 通知 | 批准、否決、失效各通知行程所有成員（動作者本人除外）；`notifications` 加入 `supabase_realtime`，推送依 RLS 只到收件人 |
| 一致性檢查 | `tooling/approval-sql-consistency.test.ts` 比對 SQL 自動套用清單與 `approvalRule` |

## 安全審查（S-15）

| 檢查 | 結果 |
|---|---|
| 權限 | 三個公開函式都先檢查角色；不存在的提案與無權限回傳同一錯誤，不洩漏提案是否存在 |
| 批准者偽造 | 批准者取自 session，不接受參數 |
| 跨行程修改 | 每個操作只能修改提案所屬行程的項目，否則拒絕 |
| 繞過批准 | 自動套用只限 service role 與自動類別；內部寫入函式對 authenticated、anon、service role 都不開放 |
| search_path | 全部函式 `search_path = ''` |
| 並行 | 審查時發現兩處並修正：同分支同時批准可能死結（改為先鎖行程列）；同分支失效可能覆蓋剛否決的提案（改為只更新仍待批准的提案） |
| 錯誤內容 | adapter 不回傳資料庫錯誤訊息 |
