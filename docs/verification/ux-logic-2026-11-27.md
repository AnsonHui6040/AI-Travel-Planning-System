# 使用者邏輯重排：一個畫面一件事

| 項目 | 內容 |
|---|---|
| 原因 | 使用者回饋：介面與按鈕排列沒有考慮使用方式；要先以研究想好使用者邏輯，例如不用捲動就能使用，而不是把所有元素放進同一頁 |
| 分支 | `feat/ux-logic` |
| 日期 | 2026-11-27 |
| 狀態 | 架構已批准（2026-11-27 使用者選定：固定四個分頁，「現在」依階段）；已實作，自動驗證通過，真機項目待測（第 9 節） |

## 1. 現況量測（示範行程，390×812 與 1280×800）

| 編號 | 頁面 | 量測 | 問題 |
|---|---|---|---|
| U1 | 今天（390） | 第一個行程項目在第 1.7 個畫面；第一個畫面全是 Morning Check 十列 | 旅行中最需要的「下一站、最遲離開」要捲近兩個畫面 |
| U2 | 今天（390） | Incident Mode 按鈕在第 1.3 個畫面 | 出狀況時找不到入口 |
| U3 | 行程分頁 | `position: static`，捲動後消失；六個分頁 | 基線、Actual Timeline、成員、我的資料不在分頁內，只能由頁內連結進入 |
| U4 | 首頁 | 建立行程表單（兩個輸入欄）佔畫面中段；行程清單只是一行文字 | 最常做的是開啟行程，最醒目的卻是建立表單 |
| U5 | 候選 | 每個候選展開八項評分；三個候選 2.5 個畫面 | 無法快速比較與選擇 |
| U6 | 每日 | 3.7 個畫面、0 個按鈕 | 三天全部展開，無法跳到某一天 |
| U7 | 規劃流程 | 基線、研究、核實、每日、批准沒有步驟提示 | 不知道目前在哪一步、下一步做什麼 |
| U8 | 今天（1280） | 內容寬 800px 單欄、2.5 個畫面 | 寬度沒有使用 |

## 2. 研究依據

| 依據 | 內容 | 用在 |
|---|---|---|
| Hoober，UX Matters（2013） | 觀察使用中的手機握法：單手 49%、一手托一手點 36%、雙手 15% | 主要按鈕放在畫面下方三分之一，拇指可及 |
| Nielsen Norman Group，Scrolling and Attention（2018） | 第一個畫面佔 57% 的瀏覽時間，第二個 17%；第一個畫面內六成五以上集中在上半 | 每個畫面最重要的資訊放在上半，完成工作不需要捲動 |
| Nielsen Norman Group，Hamburger Menus | 隱藏式導覽在手機與電腦的體驗都較差，主要影響沒有頁內連結的內容 | 主要導覽常駐顯示；所有頁面都要有固定入口 |
| Apple HIG，Tab bars | 分頁數越少越好，每多一個分頁就更難找到資訊；分頁固定，不因狀態改變 | 底部固定四個分頁 |
| Apple HIG，Live Activities | 有開始與結束的工作要能一眼看到進度 | 旅行中的「下一站」卡片 |
| UI/UX Pro Max：`primary-action`、`content-priority`、`progressive-disclosure`、`bottom-nav-limit`、`state-preservation` | 每畫面一個主要按鈕；手機先顯示核心內容；細節逐步展開；底部導覽最多五項；返回時保留位置 | 全部畫面 |

## 3. 使用者與情境

| 情境 | 裝置與姿勢 | 要完成的事 | 頻率 |
|---|---|---|---|
| 旅行中 | 手機、單手、走路或在車上、可能沒有網路 | 看下一站與最遲離開時間、出發、出狀況時找替代方案、批准同行者的提案 | 每天數十次 |
| 規劃中 | 電腦為主，也會用手機 | 填基線、研究、核實與選擇候選、排每日、批准 | 出發前數次，每次較長 |
| 同行者 | 手機 | 看今天、批准或否決提案 | 有提案時 |
| 旅後 | 手機或電腦 | 標記每個項目、決定是否保存記憶 | 一次 |

## 4. 原則

1. 一個畫面一件事：完成那件事所需的資訊與主要按鈕，在 390×844 內不用捲動。清單類畫面只有清單本身可捲動，標題與按鈕固定。
2. 打開就到現在該做的事：行程依階段（規劃中、旅行中、旅後）決定第一個分頁的內容。
3. 主要按鈕在下方三分之一；每個畫面只有一個 primary。
4. 細節另開畫面：清單每項一行，點進去才看評分、來源、照片。
5. 底部四個固定分頁，所有頁面兩次點擊內可到。

## 5. 架構

```
首頁（行程清單）
 ├─ 行程卡（目前行程在最上，顯示下一站）
 └─ 新行程（另開畫面）

行程內：底部固定分頁
 ┌──────────┬──────────┬──────────┬──────────┐
 │ 現在     │ 行程     │ 提案 (2) │ 更多     │
 └──────────┴──────────┴──────────┴──────────┘
 現在：依階段顯示
   規劃中 → 步驟列（基線→研究→候選→每日→批准）與目前步驟的主要按鈕
   旅行中 → 下一站卡、今天時間軸、出狀況
   旅後   → 一次標記一個項目，之後是記憶提案
 行程：日期切換 → 該日項目（每項一行）→ 項目詳情
 提案：待批准清單 → 提案詳情（影響範圍、批准）；Change Log 另一段
 更多：基線、候選、成員、我的資料、記憶、Actual Timeline、設定
```


### 電腦（1280）

同一架構；底部分頁改為左側欄。清單類畫面為左清單、右詳情；「現在」為三欄：下一站、今天時間軸、檢查與 Backup，不用捲動。

## 7. 驗收（實作時以 E2E 量測）

| 項目 | 標準 |
|---|---|
| 不用捲動 | 「現在」三種狀態、提案詳情、候選詳情、出狀況每一步：示範資料下 `scrollHeight ≤ innerHeight`（390×844 與 1280×800） |
| 主要按鈕位置 | 手機上 primary 的頂端在畫面高度 2/3 以下 |
| 導覽 | 底部分頁固定顯示、四項；每個頁面從分頁兩次點擊內可到 |
| 主要按鈕數 | 每個畫面最多一個 primary（沿用 `ui-buttons.test.ts`） |
| 返回 | 從詳情返回清單時保留捲動位置與篩選 |

| 規格 | 實作 | 檔案 |
|---|---|---|
| 底部四個分頁 | 現在、行程、提案（待批准數）、更多；手機固定在底部（64px 加 safe area），1024px 以上改為左側欄。分頁不因狀態改變，其他頁面都歸「更多」 | `components/trip-nav.tsx`、`app/shell.css`、`app/trips/[tripId]/layout.tsx`、`lib/server/trip-nav.ts` |
| 更多 | 旅行基線、候選、Morning Check、Actual Timeline、Incident 紀錄、旅後回顧、成員、我的聯絡資料、行程記憶、我的記憶、AI 設定、API key、所有行程；旅前自動再核實的開關由每日頁移到這裡 | `app/trips/[tripId]/more/` |
| 現在：依階段 | 行程狀態 baseline、planning 為規劃中；locked、in_progress 為旅行中；ended、archived 為旅後（`tripPhase`） | `app/trips/[tripId]/today/page.tsx`、`lib/now-view.ts` |
| 現在：規劃中 | 步驟列 基線、研究、候選、每日、批准，只顯示目前步驟與它的主要按鈕；已有批准的日期時前面步驟視為完成（`planningSteps`） | `today/now-planning.tsx` |
| 現在：旅行中 | 下一站卡片（時間、最遲離開與倒數、交通、離開前檢查）、Morning Check 一行摘要（開啟 `/today/check`）、今天時間軸（已過、目前、下一站）、動作列 出狀況 與 開始導航（primary，`directionsUrl`）。下一站與倒數在瀏覽器端每分鐘重算（`nowStop`）。1280 為三欄：下一站、時間軸、檢查與 Backup | `components/now-trip.tsx`、`today/now-trip-screen.tsx`、`today/check/page.tsx` |
| 現在：旅後 | 一次標記一個項目（單選選項 + 儲存，下一項），全部標記（行程封存）後產生旅後記憶提案 | `today/now-post.tsx`、`today/post-trip-step-form.tsx` |
| 行程分頁 | 日期切換，每項一行（時間、名稱、核實狀態或 At Risk）；草案日在這一頁批准（一天一個 primary）。項目詳情另開：時間、停留、下一站、交通、最遲離開、可移動範圍、照片、離開前檢查、調整時間（送出為提案）、導航 | `app/trips/[tripId]/days/`、`app/trips/[tripId]/items/[itemId]/page.tsx`、`components/adjust-time.tsx` |
| 候選 | 篩選（全部、未核實、已核實、Backup）放在網址；每項一行；詳情另開（八項評分、核實的事實、推薦原因、來源、研究方向、相關的交通動線比較） | `app/trips/[tripId]/candidates/` |
| 提案 | 清單每項一行，Change Log 另一段（`?view=log`）；詳情顯示影響範圍（日期與每個變更，以項目名稱描述）、批准（primary）與否決 | `app/trips/[tripId]/proposals/`、`lib/server/proposals.ts` |
| 出狀況 | 第 1 步選發生什麼事（九個選項）再填細節；第 2 步最多三張替代方案卡（差異、交通、影響）；第 3 步確認並批准。Current State Snapshot 與完整比較表另開（`?view=compare`） | `app/trips/[tripId]/incident/` |
| 首頁 | 行程卡片，目前行程在最上（進行中，或日期涵蓋今天，或最近出發），旅行中顯示下一站；新行程另開畫面 `/trips/new` | `app/page.tsx`、`app/trips/new/page.tsx`、`lib/home-order.ts` |
| 返回保留 | 清單的捲動區以 `ScrollKeeper` 把位置存在 sessionStorage（鍵含篩選）；篩選在網址，返回連結帶回篩選 | `components/scroll-keeper.tsx` |
| 1280 | 清單類畫面左清單、右詳情（`.split`）；手機上清單與詳情分成兩個畫面 | `app/shell.css` |

與規格不同之處：

| 項目 | 規格 | 實作 | 原因 |
|---|---|---|---|
| 候選詳情的「設為 Primary」 | 有按鈕 | 沒有 | 目前沒有由使用者改候選角色的寫入路徑；新增需要新的資料庫函式，本次不改資料與安全函式 |
| 出狀況第 3 步 | 確認送出為提案 | 確認並批准 | `start_incident` 產生替代方案時已建立待批准提案（T38）；第 3 步以 `approve_proposal` 批准其中一個，其他提案同時出現在「提案」分頁 |
| 下一站 | 未定義延誤時 | 依排定時間判斷目前所在項目 | 沒有實際位置時以排定時間為準；超過最遲離開時倒數變為「已超過」並以點綴色標示，下一站開始後改由項目詳情開啟離開前檢查 |
| 兩次點擊 | 所有頁面 | 所有區段頁面兩次內；單一項目的頁面（照片、候選詳情、提案詳情）經由其清單 | 項目頁面需要先選擇項目 |
| 離線 | 未提 | `/offline-today` 仍顯示完整的當日清單與調整時間 | service worker 以同一網址回應；線上版為新的「現在」 |
