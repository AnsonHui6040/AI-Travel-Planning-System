## 設計

| 項目 | 說明 |
|---|---|
| 儲存 | `public.save_api_key(owner, provider, secret, tested_at)`：以 `vault.create_secret` 加密，`api_key_records` 只存 Vault 編號與末四碼。同一供應商更新時沿用同一個 secret |
| 解密 | 伺服器請求：`decrypt_api_key(owner, provider)`，owner 由伺服器取自 `supabase.auth.getUser()`。背景 job：`decrypt_job_api_key(job_id, provider)`，資料庫依發起人取 key（C-12） |
| 權限 | 三個函式擁有者為 `atps_key_keeper`（只有 Vault 與 `api_key_records` 所需權限），只授權 `service_role`。使用者以本人 session 檢視（末四碼）與刪除本人的紀錄（RLS） |
| 刪除 | `api_key_records` 刪除時（使用者刪除或帳號 cascade）由 trigger 刪除 Vault secret |
| 格式 | 可列印 ASCII、不含空白、8–512 字元；前端、core、資料庫三處相同 |
| service role | 只在 `apps/web/lib/server/supabase.ts`（`server-only`）建立，用於上述三個函式（C-09） |
| 掛鉤 | core 的 `KeyTester` 與 `createKeyTesterRegistry()`；`apps/web/lib/server/api-keys.ts` 的 `keyTesters` 由 T13（三家 AI）、T19（Google Maps）、T22（ODPT）註冊。尚未註冊掛鉤的供應商直接儲存，畫面標示「尚未測試」 |
| 遮罩 | `@atps/security` 的 `redactSecrets`：遮罩已知 key 與常見格式，供 T17 的 log 與 AI 請求紀錄使用（S-10） |
| 認證方式 | 本 Task 只實作 `api_key`；`plan_oauth` 依 C-06 預留（T11 的 `CredentialProvider`，`available: false`） |
| 設定頁 | `/settings/api-keys`：五個供應商各一組，顯示末四碼或「尚未設定」、儲存、刪除；未登入顯示「請先登入」。Server Action 檢查登入與速率限制（每分鐘 10 次），Origin 由 Next.js 比對 |

## 安全審查（S-15）

| 檢查 | 結果 |
|---|---|
| 跨使用者 | 使用者無法呼叫儲存、解密函式，也無法讀 Vault；只能看到與刪除本人的紀錄；擁有者一律取自 session |
| service role | 只在 `server-only` 模組使用，只呼叫 key 相關函式；client bundle 掃描不含 service role key |
| 函式權限 | `security definer`、`search_path = ''`，擁有者為最小權限角色；收回 public、anon、authenticated 的執行權限 |
| 背景 job | 解密只依 job 發起人，不接受擁有者參數 |
| 錯誤訊息 | 全部改為固定文字，不帶出 key 或資料庫訊息 |
| 測試呼叫掛鉤 | 掛鉤回傳的原因含 key 時改為固定訊息；掛鉤拋出錯誤時不儲存 |
| 本機設定 | `apps/web/.env.local` 填入本機 Supabase 的開發用 service role key，該檔不納入版本控制 |

沒有發現可被利用的漏洞。
