## 設計

| 項目 | 說明 |
|---|---|
| 計算 | core 的 `planIncident`（純函式，不呼叫 AI 或外部 API）。輸入為事件、目前時間、行程與候選、交通估算（T28）、位置、同行者、行李、Morning Check 的天氣 |
| 分級 | 依決策 0004：延誤以 `classifyDelay`；排隊過長 L2；休館、鐵路中斷 L3；新增大雨 L3（重排至下一個 Hard Constraint）、航班改期 L4；提早完成與取消時段不分級 |
| Snapshot | 時間、位置（小數第三位）、目前項目、同行者、行李、天氣、即時交通（目前沒有資料時為「無即時資料」）、已完成活動、下一個 Hard Constraint（項目的限制類別或固定活動，以及基線的固定活動）、最遲到達（開始前 15 分鐘） |
| 重算範圍 | 局部：到下一個 Hard Constraint 為止（延誤影響之後 1–2 個活動；休館、取消只替換該項目；大雨替換雨停前的天氣敏感項目）；全日：極端天氣（L4），Hard Constraint 保留；整趟：航班改期 |
| 方案次序 | 延誤時先「壓縮緩衝」（延後開始、保留結束），再依同區域、鄰近區域（當天其他項目的分區）、交換今日順序（下雨時只在換到的時段已雨停時交換）、使用另一日候選、刪減活動；取前三個，不足三個時補上刪減活動 |
| 候選條件 | 尚未排入、Verified 或 Partially Verified、不是 Hard Constraint；下雨時只用天氣依賴低的候選；Standby 優先，再依優先級；放入時段時至少停留 30 分鐘（或建議停留的一半），並符合營業時段 |
| 交通 | 有 T28 估算時以 `comparePlans` 取推薦、最快、最便宜、最舒適；沒有估算時以預設 30 分鐘計算並在畫面註明 |
| 比較表 | 新活動、到達時間、最遲離開、成本、步行、轉乘、行李適合度、天氣風險、是否影響晚餐、對明日影響、體驗損失、推薦度（1–5）；推薦度最高者標示推薦 |
| 版本類型 | 第 2.7 節判定修正：候選清單沒有日期，候選排入某一天或項目移回候選清單屬同一天內的單一景點改變（Minor）；跨日移動與結構變更仍為 Major（`versions.test.ts`） |
| 寫入 | Server Action 只接受事件與現況欄位（strict schema），行程資料由伺服器以使用者 session 讀取後重新計算；`start_incident`（擁有者 `atps_change_writer`，Owner、Companion，行程已鎖定或進行中）建立 incident 與最多三個待批准提案（同一 base version、同一即時分支，提出者為本人），比較表存於 incident 的 snapshot（上限 32 KB），通知其他成員；不改動行程 |
| 生命週期 | 行程鎖定後，trigger `sync_lifecycle_with_schedule`：候選經提案排入某一天為「已修改」（當日行程會顯示）；已排入的項目移回候選清單須重新核實：生命週期為「待核實」、核實狀態為「未核實」（Conflict 維持 Conflict），重新核實前不會被每日草案或 Incident Mode 選用；上次核實時間、來源與事實主張保留（2026-11-26 使用者決定，migration `20261126030000`）。同一個更新已自行設定生命週期時（例如 `approve_day`）不介入 |
| 畫面 | 當日行程新增 Incident Mode 入口（Owner、Companion）；離開前檢查建議進入時附連結。入口頁選擇事件、受影響項目、同行者、行李，可取得目前位置；結果頁顯示 Snapshot、重算範圍、比較表（390 寬度不水平捲動）、各方案內容與交通、批准與否決 |
| 時間 | 伺服器時間為準；在當天開始之前進入時以 00:00 計算 |

## 安全審查（S-15）

| 檢查 | 結果 |
|---|---|
| 權限 | 只有 Owner、Companion（資料庫以 `can_edit_trip` 檢查；Viewer、非成員被拒，pgTAP）；提出者取自 session；批准沿用 T34 的 `approve_proposal` |
| 寫入範圍 | `start_incident` 不改動行程項目；方案只能是需批准的變更種類（自動套用類別被拒）、只能調整同一行程的項目、最多三個；snapshot 必須是物件且不超過 32 KB（pgTAP） |
| 輸入 | Server Action 以 strict schema 驗證，拒絕多餘欄位；行程資料一律由伺服器重新讀取計算，不採用瀏覽器送來的方案；錯誤訊息固定，log 經 `createLogger` |
| 位置 | 只在使用者按下按鈕時以瀏覽器定位取得，只送出一次；保存到小數第三位（約 100 公尺），只有行程成員可讀；不送往外部服務 |
| 外部呼叫與 AI | 沒有。計算為確定性規則 |
| 呈現 | 文字以 React 呈現，沒有 `dangerouslySetInnerHTML` |
| trigger | `sync_lifecycle_with_schedule` 只在行程鎖定後、排程日期由有變無或由無變有時改變同一列的生命週期，不讀寫其他資料表（除了讀取行程狀態） |

沒有發現可被利用的漏洞。
