## 設計

| 項目 | 說明 |
|---|---|
| 可行性檢查 | `checkDay`（`packages/core/src/feasibility.ts`）逐日核查十一項。會擋下的四項：營業時間、休館日、交通時間、固定活動前後緩衝。其餘七項只提醒：預約、首末班車、餐飲時段、步行量、行李、體力、天氣依賴 |
| 數值 | 固定活動前後另加 15 分鐘；首班車 05:30、末班車 23:30（前後各加 30 分鐘交通）；步行 90 分鐘；活動時間 480 分鐘，基線有體力備註時 360 分鐘 |
| 營業時段 | `availability`：依星期或指定日期；指定日期優先；沒有資料時視為未知、不限制；有資料但當天沒有時段即休館。核實結果通過（Verified、Partially Verified）時經 `set_item_availability` 寫入 |
| 排入 | `planFeasibleDays`：排入時即遵守會擋下的條件（營業時段內、到下一站的交通、固定活動前後的緩衝），排入後逐日驗證。放不下的項目回到地理分區、留在 Candidate List，並標示原因 |
| 批准 | `approve_day`（以 `atps_change_writer` 執行，Owner、Companion）：比對 base version，檢查日期、時段格式與重疊、項目屬於此行程且為已核實的 Primary；項目由已核實進入已批准並寫入時段與可移動範圍；該日為已批准；建立新 Master Version（v1.0 起，每批准一天主版號加一）；通知其他成員 |
| 鎖定 | 所有日期都批准後，行程由規劃中進入已鎖定，已批准的項目進入已鎖定 |
| 伺服器重新計算 | Server Action 不採用瀏覽器送來的時段：以使用者 session 重新讀取並執行 `planFeasibleDays`，該日仍有會擋下的問題時不送出 |
| 已批准的日期 | 畫面顯示資料庫中的時段，不再重排；其餘日期仍是草案 |

## 安全審查（S-15）

| 檢查 | 結果 |
|---|---|
| 寫入權限 | `approve_day` 只授權 authenticated，呼叫者取自 session，再以 `can_edit_trip` 限 Owner、Companion；Viewer 與非成員被拒（pgTAP）。`set_item_availability` 只授權 service_role |
| 正式行程寫入（S-01） | 只經 `atps_change_writer` 擁有的函式；本 Task 只新增欄位層級權限（`status`、`movable_from`、`movable_to`、`lifecycle_status`、`days`） |
| 竄改時段 | 編輯者可直接呼叫 `approve_day` 送出自訂時段；資料庫仍檢查所屬行程、核實狀態、Primary、時段格式與重疊，所以只能影響自己有編輯權的行程 |
| 輸入驗證 | 營業時段只接受 `date`、`weekday`、`start`、`end`，時間格式與先後由資料庫檢查；AI 輸出經 schema 檢查 |
| 呈現 | 名稱與提醒以 React 呈現；錯誤訊息不含資料庫內容 |

沒有發現可被利用的漏洞。
