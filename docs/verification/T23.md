## 設計

| 項目 | 說明 |
|---|---|
| 三類限制分類 | `classifyBaseline`（`packages/core`）。Hard Constraint：旅行日期、航班、住宿、已付款固定活動、已付款項目、排除地點。Strong Preference：未付款固定活動、必去地點、體力限制、預算。Flexible：交通偏好、攝影需求。沒有填寫的項目不列入 |
| 矛盾檢查 | `checkBaseline`。矛盾（不可確認）：航班抵達不晚於出發、住宿退房不晚於入住、住宿或活動超出旅行日期、住宿夜晚重疊、活動結束不晚於開始、活動彼此重疊、活動與航班時間重疊、入住後 60 分鐘內要到另一區的活動、同一地點同時必去與排除。提醒（可確認）：有夜晚沒有住宿、航班日期離旅行日期超過一天、入住後 60 分鐘內有活動但地區未填 |
| 數值 | 入住後到另一區至少 60 分鐘；沒有結束時間的活動以 60 分鐘計算重疊。只用於標示，不改動資料 |
| 固定活動的地區 | `tripBaselineData` 的固定活動加入 `area`（可為 null），用於 E5 這類跨區檢查 |
| 儲存與確認 | 資料庫函式 `save_trip_baseline`、`confirm_trip_baseline`，擁有者為新角色 `atps_baseline_writer`（只有基線表與行程狀態、日期、時區欄位的權限），呼叫者取自 session。限 Owner、Companion，且行程在「基線」狀態。確認時記錄 `confirmed_at`，行程進入「規劃中」，日期與時區取自基線（時區須在 `pg_timezone_names`） |
| 確認前檢查 | Server Action 以使用者 session 讀取草稿，重新以 schema 與 `checkBaseline` 檢查，有矛盾時不呼叫確認函式 |
| 確認後 | 再儲存回應「基線已確認，之後的修改請提出變更提案」；頁面改為唯讀 |
| 畫面 | `/trips/[tripId]/baseline`：表單依區塊填寫，右側（390 寬度在下方）即時顯示矛盾與限制分類。Viewer 與確認後只顯示分類與檢查結果 |
| 權限收緊 | Supabase 預設權限讓 authenticated 有 `trips` 的 UPDATE（RLS 沒有 update policy，原本只是更新 0 筆）。本 Task 收回，行程狀態只可經函式轉換；`05_apply_change.test.sql` 的對應測試改為預期 42501 |
| E5 評估方式 | 矛盾檢查是確定性規則，不呼叫 AI，所以放在 `evals/baseline/`，不需要錄製回應，每個場景執行一次 |

## 測試順序

先新增 `packages/core/src/baseline.test.ts`、`apps/web/lib/server/baseline-core.test.ts`、`evals/src/baseline.test.ts` 與 `supabase/tests/13_trip_baseline.test.sql`，執行確認失敗（RED：三個測試檔模組不存在；pgTAP 19 項中 17 項失敗，直接寫入被拒的 2 項原本就通過）。實作後通過（GREEN）。

實作中發現兩個問題，都已修正並以測試確認：

1. 資料庫函式檢查缺少日期時，`jsonb_typeof` 對不存在的鍵回傳 null，條件不成立；改用 `coalesce`，由 pgTAP「缺少日期時拒絕」確認。
2. 第一次截圖時發現儲存後「已付款」核取方塊顯示未勾選：React 在 Server Action 完成後重設 form，受控的核取方塊與狀態不一致。改為輸入欄位不放在 form 內，E2E 加上儲存後仍為勾選的斷言。這個斷言是在修正後加入，沒有先單獨確認失敗。

## 安全審查（S-15）

| 檢查 | 結果 |
|---|---|
| 權限 | 寫入只經兩個 security definer 函式，擁有者是只有必要欄位權限的角色；呼叫者取自 session；Viewer、非成員回應 42501；使用者沒有 `trip_baselines` 寫入權與 `trips` 的 UPDATE |
| 狀態 | 確認只能從「基線」進入「規劃中」，已確認後不可再儲存或確認（55000） |
| 輸入 | 伺服器以 strict schema 檢查（多餘欄位拒絕），JSON 上限 64 KB；資料庫另檢查物件型別、大小與日期欄位 |
| 繞過檢查 | 有編輯權的成員可以直接呼叫確認函式而略過矛盾檢查；這只影響自己有權編輯的行程，不涉及他人資料。確認函式仍檢查日期與時區 |
| 輸出 | 頁面以 React 呈現文字，沒有 `dangerouslySetInnerHTML`；回應訊息與 log 不含基線內容 |

沒有發現可被利用的漏洞。
