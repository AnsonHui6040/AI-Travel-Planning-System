## 設計

| 項目 | 說明 |
|---|---|
| 事實主張 | Research 候選與 Verification 結果新增 `facts`（營業時間、休館日、門票、預約、交通服務，各附來源；沒有時為空陣列）。主張連同提出的模型存入 `itinerary_items.fact_claims` |
| 證據順序 | `EVIDENCE_ORDER`：設施官方、官方交通或旅遊局、可靠第三方、使用者評論。`resolveFact` 採用最高等級的來源；最高等級的來源之間不一致時為 conflict。寫法差異（全形半形、空白、各種破折號）不算不一致 |
| 核實狀態 | `crossCheck`：任一事實 conflict 即為 Conflict；營業時間、休館日、門票、交通服務只有非官方來源時最高為 Partially Verified；Research 與 Verification 同一家時最高為 Partially Verified（D07）；其餘依 Verification 的判定。判定結果存入 `itinerary_items.facts` |
| 生命週期 | Verified 與 Partially Verified 進入「已核實」；Unverified 與 Conflict 留在「待核實」，不得進入行程草案（T07 的 `canEnterDraft`） |
| 背景 job | `research-job` 在四個研究方向完成後合併重複候選，再把尚未核實的候選每 10 個一批交給 Verification（每批一個 step，最多 120 個） |
| 寫入 | 資料庫函式 `merge_duplicate_candidates`、`apply_verification`（只給 service_role，擁有者 `atps_verification_writer`）。兩者都檢查研究 job 執行中、發起人仍為 Owner 或 Companion、行程已確認基線；項目必須屬於該行程且尚未進入行程草案。`apply_verification` 在資料庫再套用一次同一家上限 |
| 畫面 | Candidate List 顯示核實的事實（採用的值與來源等級，無法判定時以紅字標示）與核實模型；列出候選、待核實與已核實的項目 |

## 測試順序

先新增 `packages/core/src/dedupe.test.ts`、`packages/core/src/cross-check.test.ts`、`apps/web/lib/server/verification-core.test.ts`、`evals/src/crosscheck.test.ts` 與 `supabase/tests/15_cross_check.test.sql`，執行確認失敗（RED：單元測試 22 項失敗、一個測試檔模組不存在；pgTAP 因欄位不存在未執行）。實作後通過（GREEN）。

實作中發現兩個問題，都由 pgTAP 確認修正：

1. 生命週期以 `case` 運算式更新時型別為 text，需轉型。
2. `apply_verification` 讀取項目時用了 `FOR UPDATE`，會套用 update policy，草案以後的項目讀不到，回應「不屬於此行程」而不是「已進入行程」。改為只讀取，由 UPDATE 本身鎖定。

## 安全審查（S-15）

| 檢查 | 結果 |
|---|---|
| 寫入範圍 | 兩個函式只給 service_role；擁有者只能更新核實相關欄位，刪除只限候選與待核實的項目 |
| 權限 | 背景 step 與資料庫函式各自檢查 job、發起人角色與行程狀態；項目必須屬於 job 的行程 |
| 獨立核實 | 同一家上限在伺服器（`crossCheck`）與資料庫各套用一次，AI 無法以輸出繞過 |
| Prompt injection | 候選資料（含 Research 的文字與來源）以資料區塊傳給 Verification（S-03）；核實結果只能指向本批項目，否則整份拒絕；含圖片網址或 API key 的輸出被拒 |
| 輸出呈現 | 事實值以 React 文字呈現；沒有 `dangerouslySetInnerHTML` |
