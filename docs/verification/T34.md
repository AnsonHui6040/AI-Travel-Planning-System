## 設計

| 項目 | 說明 |
|---|---|
| 先到先得 | 批准經 core 的 `applyChange`（第 2.6 節批准規則、第 2.7 節版本類型）與 T09 的 `approve_proposal`：鎖定行程列後比對 base version，不同即失效（SH-04）。本 Task 沒有新增資料庫變更 |
| 批准者 | Server Action 只接受提案編號；批准者由資料庫取自 session，畫面先檢查 Owner、Companion（Viewer 看不到按鈕，資料庫也會拒絕） |
| 通知（SH-06） | 套用、否決、失效由 T09 的資料庫函式寫入 `notifications`；`LiveNotifications` 以瀏覽器的 Supabase client（anon key 與本人 session，C-09）訂閱本人的新通知，收到同一行程的通知即重新整理畫面。訂閱前先設定 Realtime 授權，否則 RLS 不會推送 |
| Change Log | 每個版本顯示版本號、摘要、Major 或 Minor、提出者（成員名稱或 AI 角色與模型）與批准者（自動套用時標示） |
| 提案列表 | 最近的提案依提出時間排列，處理後留在原位置並標示狀態；行程在提出後已更新的待批准提案會提示「批准時會失效」 |
| CSP | `connect-src` 只另外允許 `NEXT_PUBLIC_SUPABASE_URL` 的 http(s) 與 ws(s)；不是 http(s) 網址時不加入 |
| SH-05 | 離線排隊的修改於同步時視為提案、依同樣的版本檢查處理；離線同步於 T35 |
