# 0011 完整的行程編輯

| 項目 | 內容 |
|---|---|
| 日期 | 2026-11-28 |
| 狀態 | 使用者選定，已實作（`docs/verification/EDIT-full.md`） |
| 原因 | 使用者在 iPhone 上測試後指出「行程要有完整的編輯功能」：只能逐項打開編輯、鎖定後連 Owner 的修改都成為提案、只能設定開始時間、沒有行程層級的編輯，且 390px 有多個表單版面錯誤 |
| 取代 | 決策 0010 第 2 節「編輯生效方式」與第 3 節 E 的「寫入」列 |

## 1. 使用者選定（2026-11-28）

| 決定 | 內容 |
|---|---|
| 鎖定後誰可以直接修改 | Owner 的修改直接套用，留下 Change Log 並通知其他成員；Companion 的修改照舊成為待批准提案 |
| 清單編輯 | 行程分頁的清單內編輯模式（類似 iOS 提醒事項與 Wanderlog） |
| 其他功能 | 四項都做：開始與結束時間加自動順延、行程層級編輯、插入／複製／整天交換、兩站之間的交通 |

## 2. 生效方式（取代決策 0010 的編輯規則）

| 情況 | Owner | Companion | Viewer |
|---|---|---|---|
| 行程規劃中，影響的日期都是草案 | 直接寫入（不產生版本） | 直接寫入（不產生版本） | 不可 |
| 行程規劃中，影響已批准的日期 | 直接套用（Change Log、通知） | 待批准提案 | 不可 |
| 行程已鎖定或旅行中 | 直接套用（Change Log、通知） | 待批准提案 | 不可 |
| 行程已結束或已封存 | 不可 | 不可 | 不可 |

| 項目 | 規格 |
|---|---|
| 直接套用的寫法 | 資料庫函式 `apply_owner_change`（擁有者 `atps_change_writer`）檢查呼叫者是 Owner，以 Owner 的名義建立提案並在同一個交易內以 `commit_proposal` 套用。因此與 Companion 的提案相同：寫入 `versions`（Change Log）、通知其他成員（`proposal_applied`）、行程版本已變更時失效（SH-04） |
| 直接套用的檢查 | 只接受編輯的四種操作（新增、修改、刪除、排程）；排入的日期須在基線期間內；排入的項目須為已核實、部分核實或使用者確認的 Primary（D07） |
| Companion 的提案 | 照舊以 `applyChange` 與 `approve_proposal` 批准，批准規則不變 |
| AI | 不變：AI 不可直接寫入（S-01），`commit_proposal` 拒絕 AI 提出的新增、修改、刪除 |
| 草案不產生版本 | 第 2.8 節的版本從批准每日開始（第一版 v1.0），規劃中草案日的直接寫入照舊只增加 `current_version` |

## 3. 清單內編輯模式

| 項目 | 規格 |
|---|---|
| 進入 | 行程分頁當日標題旁的「編輯」 |
| 每列 | 拖曳把手（滑鼠與觸控；聚焦後上下鍵）、在後面插入、刪除（`window.confirm`，按「完成」才儲存）、開始與結束時間、44px 上移與下移 |
| 插入 | 在某項後面輸入名稱、類型、停留，加入為使用者新增的項目 |
| 自動順延 | 時間、停留或順序改變時，從第一個改變的位置開始，後面每一項的開始時間為「原本的時間」與「前一項結束＋交通」較晚者；遇到固定活動或預訂（Hard Constraint，不移動）時排到其後；超過當天的項目標示排不下、不能送出。只往後移，不往前拉 |
| 拖曳後的時段 | 每個位置沿用該位置原本的開始時間（保留午休等空檔），停留時間跟著項目 |
| 預覽 | 順延的項目標示「順延」，下方列出；勾選「不要順延」時只改這一項，重疊時伺服器拒絕並提示 |
| 完成 | 一次送出一天的順序、時間、刪除與插入：草案日一個交易（`edit_trip_items`，擁有者 `atps_item_editor`）；Owner 一筆 Change Log；Companion 一個提案 |
| 純函式 | `packages/core/src/full-edit.ts`：`shiftDay`、`reorderDesired`、`batchOperations`、`swapDaySlots`、`tripDateChange`、`legGapMinutes`、`editMode` |

## 4. 時間、複製與整天交換

| 項目 | 規格 |
|---|---|
| 開始與結束時間 | 編輯項目畫面可設定開始與結束；結束空白時依停留計算 |
| 複製 | 同一天接在原項目之後（沒有排入時放進候選清單），成為使用者新增的項目 |
| 整天交換 | 編輯模式下選另一天，兩天的項目互換日期、時間不變；固定活動與預訂屬於日期，不跟著交換。以 `window.confirm` 確認 |

## 5. 兩站之間的交通

| 項目 | 規格 |
|---|---|
| 顯示 | 相鄰兩項之間顯示交通方式與分鐘：成員輸入優先，其次 T28 的交通估算（含緩衝），都沒有時顯示「交通未設定」 |
| 輸入 | 步行、電車、公車、計程車、開車與門到門分鐘（0 到 600），存在 `travel_legs`（每對項目一列） |
| 權限 | Owner、Companion 直接寫入（RLS）；Viewer 唯讀；非成員看不到。交通是估算而非行程內容，所以不經提案；因交通而順延的時間照第 2 節生效 |
| 排程用的間隔 | 成員輸入的分鐘依 `withBuffer` 規則加每段固定緩衝 10 分鐘（不知道轉乘次數，以 0 次計）；估算已含緩衝；沒有資料用預設 30 分鐘。同一個值也用於 `checkDay` |
| D28 | 只存兩個項目編號、交通方式與分鐘，不存 Google 的名稱、座標或路線 |

## 6. 行程設定

| 項目 | 規格 |
|---|---|
| 欄位 | 行程名稱、目的地、開始與結束日期 |
| 權限 | 只限 Owner（`update_trip_settings`，擁有者 `atps_trip_settings_writer`）；入口在「更多」的「行程設定」與行程分頁標題的「設定」 |
| 日期與基線 | 日期同步寫入已確認的 Trip Baseline v1 與 `trips` 的日期。改日期前 Server Action 以 core 的 `checkBaseline` 比較，產生新的矛盾（例如住宿超出日期）時不送出；資料庫再檢查固定活動與住宿須在新的期間內。未確認基線時只能改名稱與目的地，日期在基線頁設定 |
| 移除日期 | 以 `window.confirm` 確認；刪除該日的每日紀錄，排在那天的項目移回候選清單（鎖定後的 AI 項目依 T38 修正回到待核實） |
| 新增日期 | 規劃中為草案日；鎖定後以已批准的空白日加入，行程維持已鎖定，Owner 可直接加入地點 |
| 通知 | 其他成員收到 `trip_settings_changed` |
